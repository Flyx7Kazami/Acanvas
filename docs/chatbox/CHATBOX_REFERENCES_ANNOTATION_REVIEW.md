# Chatbox 引用与即时画布批注方案审查

日期：2026-10-08（Asia/Shanghai）。

审查对象：[Chatbox 引用与即时画布批注计划](CHATBOX_REFERENCES_ANNOTATION_PLAN.md)。

关联资料：[Codex 消息桥调研](CODEX_MESSAGE_BRIDGE_RESEARCH.md)、[项目计划](../PLAN.md)。

## 1. 总体结论与审查范围

方案方向可行，现有草稿 revision、任务快照、对象版本和 SQLite 短事务可以继续使用。完整实施前应补齐批注完成状态、捕获与发送的数据语义、截图提交恢复、引用预览状态以及证据资产归属。截图原型验证可以先行，原型结果决定首发支持环境与媒体范围。

本次结论来自方案与当前源码的静态核对，以及捕获、数据、交互三个方向的独立子智能体审查。浏览器能力判断参考官方资料。审查期间未运行截图原型、代码测试或操作用户白板；文中风险尚待相应实现与测试验证。

建议保留以下设计决定：

- 显式对象引用与邻近场景证据分开，区域相交只表达空间关系。
- 批注完成时保存现场，发送时形成结构化任务与可读消息。
- 用户指令、用户评论和导入参考内容保留清晰来源。
- 新批注归宿主对话绑定的草稿或任务，历史保存当时的证据。
- acanvas 本地任务与 Codex 宿主投递分别实现、分别验收。

以下建议属于待纳入实施方案的设计意见。功能状态仍为待实施。

## 2. 截图能力：首要可行性前提

原方案第 1、3、5 节已经明确实时画布截图路径待验证。这是已知的能力验证项。原型开始前还需确定首发运行环境，以及是否接受用户启动标签页共享，或要求宿主提供截图通道。

| 路线 | 能力与约束 | 建议用途 |
| --- | --- | --- |
| DOM 重建截图 | 可生成辅助预览；动态视频、GIF、隔离 iframe 与原现场的一致性需要独立证明。html2canvas 通过 DOM 表示重建图像。 | 辅助预览；准确声明捕获范围。 |
| 用户授权屏幕／标签页捕获 | 可取得实际显示画面；需要用户选择来源及瞬时激活，授权不能持久保存。需处理来源错误、取消、共享终止和刷新后重新授权。 | 接受共享步骤的独立网页环境原型。 |
| 宿主提供受控截图通道 | 更符合点击完成即捕获现场的交互；需要实际控制目标页面的宿主能力。 | 宿主能力已集成并验证的运行环境。 |

服务端另开页面生成的预览属于另一个页面实例，用户正在操作的动态现场仍需从原页面取得。当前 HTML 快照采用 DOM 重建，视频代表帧由独立解码器采样，两者各自的用途应继续明确。

依据：[html2canvas 文档](https://html2canvas.hertzen.com/documentation.html)、[W3C Screen Capture](https://w3c.github.io/mediacapture-screen-share/)、[Electron WebContents.capturePage](https://www.electronjs.org/docs/latest/api/web-contents#contentscapturepagerect-opts)。

源码：[HTML 快照](../../src/shared/html-preview-snapshot.ts)、[视频代表帧](../../src/web/videoFrameAt.ts)。

## 3. 优先修订项

### P1-01：持久保存批注完成状态，由服务端统一检查

原方案第 2 节规定捕获失败保留输入并阻止 Send，但刷新之后的恢复方式与服务端完成条件仍需定义。当前捕获 generation、preparing 等状态主要保存在前端内存，`AnnotationInput` 缺少捕获完成状态。

失败场景：修改已完成批注的区域，重新截图失败，刷新后把新区域与旧截图一起发送。CLI 发送也需要遵守同一完整性规则。

建议：

- 持久保存批注编辑版本及未完成／可发送状态。
- 完成记录绑定同一版本的目标、位置和证据资产。
- 修改目标、区域或媒体时间时使旧证据失效；仅修改评论文字时保留捕获。
- 发送事务检查新流程批注具有匹配版本的完整证据，覆盖 UI 与 CLI。
- 为旧批注明确读取和编辑语义。

验收：捕获失败后刷新、重新捕获中刷新、CLI 发送未完成批注，均保持输入并按相同规则处理。

证据：[共享类型](../../src/shared/types.ts)、[前端批注处理](../../src/web/App.tsx)的 `prepareComment`、[服务](../../src/server/service.ts)的 `sendDraft`。

### P1-02：区分捕获、发送和当前查看的时间语义

原方案第 3 节冻结捕获现场，第 4 节同时保存捕获时与发送时信息，并称历史使用发送时内容。三种时间语义及其展示入口需要明确。

失败场景：给对象 A 完成一次批注，移动 A，再完成一次批注，删除 A 后发送。两条批注分别对应不同几何，单份按对象 ID 汇总的对象数组无法完整表达。当前普通草稿发送会查询现存对象，队列编辑则优先沿用原任务的对象快照。

建议：

- 每条捕获独立保存目标、场景对象、资产与几何快照，同一对象可出现在不同捕获版本中。
- 显式 `@` 引用另按发送规则保存对象状态；发送时状态允许标记对象已删除。
- 已完成批注在原对象删除后保留完整现场；失效的显式引用提供单独处理入口。
- 历史默认展示捕获截图与其坐标中的标记；定位当前对象作为独立动作。
- 队列只改文字时保留原捕获；修改目标时产生新捕获。显式引用是否刷新发送时状态另行规定。

验收：同一对象两次捕获后删除并发送，两套几何均完整；发送后移动或缩放对象，历史现场保持；分别验证队列只改文字与修改目标后 Save edit。

证据：[服务](../../src/server/service.ts)的 `sendDraft`、[任务快照类型](../../src/shared/types.ts)、[历史投影](../../src/web/App.tsx)。

### P1-03：截图提交需要独立的结果核对与幂等语义

原方案第 4 节要求响应丢失后按 draft ID 核对任务与截图。当前 draft ID 的去重覆盖任务事务；资产上传每次生成新 ID，上传已提交但响应丢失时，重试可能产生第二份截图。

建议提供一次“提交捕获”的服务操作，以已有会话、草稿、批注 ID 和编辑版本识别此次捕获。文件完整落盘后，通过短事务登记资产与证据关联；响应丢失时先查询已提交结果。主键、唯一约束与事务可表达该关系。

文件落盘后、数据库登记前发生中断时，也需明确恢复方式。首版可保留待核对文件，优先保证已提交证据完整。

验收：分别丢弃截图上传、批注保存和 Send 响应，刷新后恢复；同一捕获身份对应一个已提交证据结果，同一 draft 对应一条任务。

证据：[资产上传](../../src/server/http.ts)、[前端 API](../../src/web/api.ts)、[发送事务](../../src/server/service.ts)。

### P1-04：引用预览采用一次性确认状态

原方案第 2 节将预览绑定当前选择、聚焦时确认，但确认或取消后仍保留选择的行为需要补齐。当前前端在发送成功、关闭批注、取消编辑和 Escape 后会程序性聚焦输入框，发送后还会保留对象选择。

失败场景：若预览始终由当前选择派生，并在 `onFocus` 确认，发送 A 后下一份草稿可能再次加入 A；手动移除引用后也可能恢复。

建议由用户选择动作生成一次待确认预览，确认、取消、移除或成功发送后消费它。程序恢复焦点只恢复输入；用户点击／Tab 进入和直接 Send 执行确认。新的选择动作可以产生下一次预览。

直接 Send 应先计算包含可见预览的请求，再判断请求是否为空。按现有方案意图，只有预览或正式引用、正文为空时也应能够发送；当前 `hasRequest` 需随之调整。

验收：发送后保留选择、关闭批注、移除引用后返回输入框，均保持预期引用集合；仅预览或正式引用时能够发送。

证据：[前端](../../src/web/App.tsx)的 `closeAnnotation`、`sendRequest`、`editRequest`、焦点恢复和 `hasRequest`。

### P1-05：会话隔离覆盖证据资产读取

原方案第 4 节要求其他宿主对话不加载新批注。当前 `state` 返回项目全部资产，资产读取按 ID 处理；新截图若沿用普通共享素材上传，即使批注结构归属清晰，另一会话仍可能取得证据资产。

建议区分项目共享素材与会话证据资产，保存证据的会话及草稿／捕获归属，并明确 state、资产读取和 CLI 上下文三个入口的规则。旧跨会话引用按已明确的历史延续规则处理。

验收：A 完成未发送批注后，B 的状态、资产候选及正常资产读取入口遵守证据归属；发送与队列编辑后继续符合规则。这里验证的是产品读取边界，宿主认证边界需按实际能力声明。

证据：[资产类型](../../src/shared/types.ts)、[状态读取](../../src/server/service.ts)的 `state`、[资产路由](../../src/server/http.ts)。

### P2-01：动态现场捕获具有有限完成条件

原方案第 3 节“截图前后状态变化则重新捕获”对播放视频、GIF、动态 HTML 缺少终止条件。父页面也无法通过对象版本完整观察隔离 HTML 内部的画面变化。

建议短暂固定应用可控的视口、几何和编辑状态；持续动态像素以捕获帧为证据，设置有限重试、总超时与取消。精确视频定位可关联呈现帧信息。视频帧回调提供媒体时间与呈现时间，整页原子截图仍需由实际捕获路径验证。

原方案还需区分用户选择的媒体时间与截图中的实际播放位置。当前选中 10–20 秒时，画布播放器可能仍停在 40 秒。可分别保存选择区间、实际捕获时间及代表帧时间；也可明确完成前把实际播放器定位到代表时间，并等待该帧呈现。音频时间选区与播放头同样需要分别解释。

验收：持续播放及动画场景能在有限时间内完成或返回可重试失败；选择区间与播放头不同步时，证据含义清楚。

依据：[视频帧回调规范](https://wicg.github.io/video-rvfc/)。证据：[媒体范围编辑](../../src/web/App.tsx)、[代表帧采样](../../src/web/videoFrameAt.ts)。

## 4. 需要明确的补充规则

| 项目 | 建议规则 | 验收重点 |
| --- | --- | --- |
| 单点与区域 | 使用明确的 `point | rect` 几何；点的屏幕命中半径只影响操作，持久坐标保持真实位置。 | 零距离点击、不同 zoom 下往返恢复。 |
| 重叠对象 | 明确区域同时落在多个对象内的目标选择。建议只有标记全部属于同一可见目标时形成对象内区域，其余形成世界区域。 | 重叠对象、内容留白、跨越上层边界但位于下层内部、改选目标。 |
| 旧跨会话引用 | 原任务快照负责初始化；后续按当前已保存草稿判断引用延续。明确移除生效点，以及取消编辑后的恢复行为。 | 仅改文字成功；移除并保存、刷新后再通过 API 加回按规则拒绝；取消编辑正确恢复。 |
| 证据保留 | 引用根包含当前草稿、任务和队列编辑中暂存的原草稿。首版继续保留未引用文件，自动清理可后续实施。 | 队列编辑提交或取消后，恢复的原草稿仍有截图。 |
| 截图坐标 | 保存实际像素尺寸、裁剪 CSS 矩形及映射；以实际尺寸计算比例。 | DPR、浏览器缩放、媒体留白、Markdown 内部滚动、局部出屏。 |
| 捕获布局 | 明确保留标记、隐藏编辑器等浮层的时序。 | 裁剪画面中的遮挡、标记可见性及捕获后的交互恢复。 |

队列编辑暂存草稿的实现见 [服务](../../src/server/service.ts)的 `beginTaskEdit` 与 `restorePreviousDraft`。裁剪捕获仍可能包含遮挡目标的浮层，参见 [Chrome Region Capture](https://developer.chrome.com/docs/web-platform/region-capture)。

## 5. 推荐实现结构与顺序

输入区建议保留 `textarea` 加正文尾部结构化引用区。当前引用统一放在正文后方，可以复用已有输入法、复制粘贴、自动增高和纯文本编辑行为。`@` 负责触发选择器，成功选择时移除本次查询片段并添加结构化引用；Escape 保留输入文字。选择器展开时 Enter 优先选择候选，关闭后恢复发送语义。正文任意位置的内联引用可在确有需求时引入结构化编辑器。

建议依次完成：

1. **截图环境与媒体原型。** 确定运行环境和用户授权交互，实测各媒体及标记叠层；分别测量捕获、编码、上传和重试总耗时，并记录图片体积。
2. **批注状态与捕获提交。** 定义持久编辑版本、完整证据记录、会话归属、结果查询和发送事务检查；使用隔离资源验证中断恢复。
3. **引用交互与历史。** 接入一次性预览、统一引用顺序、历史截图阅读和当前对象定位；保持队列编辑语义。
4. **UI 与 CLI 联合验收。** 覆盖跨会话读取、旧引用延续、对象删除、多次捕获、刷新、响应丢失、输入法、键盘、触屏、窄屏和减少动态效果。

项目现有存储结构可以承接这些调整。首轮优先解决捕获路径、状态归属与数据语义，功能完成状态以实现和验收结果记录。
